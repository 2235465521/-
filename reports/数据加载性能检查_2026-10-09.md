## 优化顺序

1. 给同类产品加入与普通搜索一致的后端结果缓存，缓存键包含关键词展开结果、排序主词、筛选、页码、分页大小、磁盘校验选项和数据版本；加入相同请求合并，防止多个 worker 同时重算。
2. 将总数缓存与页数据缓存分开：相同搜索条件的每一页不必重复 COUNT。启动/过期前预热常用首页及总数；使用有界后台刷新，在允许的短时间内先返回已有数据，同时标明更新状态。
3. 改善 EXISTS 的执行计划并验证已有索引使用情况。上述诊断已证明首页取页可由约 9.7 秒降到毫秒级；全量统计仍需单独处理。保留文件名与标准号匹配语义。
4. 统一前后端预取。目前前端预取下一页，后端又开线程预取后两页；缓存尚未生成时同一页可能重复计算，每页还重复 COUNT。先去重、限流，再决定保留哪一层预取。
5. PDF 状态校验采用短 TTL 的批量缓存及进行中请求合并。列表显示和实际下载校验分阶段处理，下载时继续验证；避免每次从列表缓存渲染仍重复查十次标准。
6. 补齐有效缓存配置、命中率和分阶段耗时指标。缓存过期时采用单次刷新锁，避免大量请求同时击穿。

本次只完成诊断与证据保存，尚未实施上述业务改动。用户电脑的网络延迟和多人并发下的排队时间需另测，但已有 SQL 证据足以解释本次 8～22 秒级的接口等待。

## 推荐实施方案：缓存、查询汇总表与下载协同

以下为后续实施建议，尚未创建表、调整索引或修改业务代码。建议分三步完成：先补齐结果缓存和重复请求合并，再建设查询汇总表与中文检索索引，同时让大包下载离开同步请求。缓存改善重复访问，汇总表和检索索引改善首次访问，后台下载避免两类请求争用 worker。

### 1. 普通视图与实体汇总表的选择

| 方案 | 对本项目的作用 | 建议 |
| --- | --- | --- |
| 普通 VIEW | 封装查询，减少 SQL 重复；不会持久保存计算结果，也不能给视图单独建索引 | 可以用于统一查询接口，不作为主要提速手段 |
| 定时或增量维护的实体汇总表 | 提前计算标准号规范化、文件名匹配、文件数量等字段；查询直接筛选和排序 | 作为主要结构优化 |
| 将标准、全部文件、全部单位直接 JOIN 成一张大表 | 一条标准可能展开成多行，继续需要去重和复杂统计 | 保留一对多关系，避免这种展开方式 |
| 独立搜索服务 | 支持更复杂的中文检索、排序和扩展 | 先验证 MySQL 检索方案，达到性能或功能边界后再引入 |

当前 MySQL 8.0 不提供原生物化视图，需要自行维护实体表。普通视图没有独立索引；它能否利用底表索引与处理算法、查询形态有关。参考 [MySQL 视图限制](https://dev.mysql.com/doc/refman/8.0/en/view-restrictions.html)和 [物化视图 FAQ](https://dev.mysql.com/doc/refman/8.0/en/faqs-views.html)。

### 2. 第一阶段：补缓存，减少相同工作

优先改造 [CacheManager](/home/zkbz01/download_file/core/cache_manager.py)、[数据库查询入口](/home/zkbz01/download_file/core/db.py)和[前端请求](/home/zkbz01/download_file/frontend/js/app.js)，先不改变搜索匹配与分页语义。

1. 为同类产品补齐结果缓存。缓存键除查询模式、关键词、筛选条件外，还应包含展开后的关键词、排序主词、规则版本和数据版本；不同查询入口使用不同命名空间。
2. 拆分总数和页数据。`count_key` 包含影响结果集合的条件，排除页码和分页大小；`page_key` 再加入页码、分页大小、排序方式及影响响应的选项。翻到第二页时复用同一条件的总数，不再重新 COUNT。
3. 合并相同的进行中请求。浏览器使用 Promise 映射；后端使用跨进程租约，使三个 Gunicorn worker 对同一缓存键只启动一次计算。仅使用进程内锁无法覆盖三个 worker。
4. 预取只保留一处，先限制为下一页，并设全局队列上限。交互请求优先，已有请求或缓存时不重复预取；不要每次查询都创建新线程预取两页。
5. 预热首页第一页及对应总数，在启动完成或数据版本发布后由单个后台任务执行。预热失败保留旧版本，避免多个 worker 同时启动全量工作。
6. 统一实际生效的缓存配置，加入过期清理、容量限制和版本隔离。当前修改 `CACHE_TTL_SEARCH` 等设置不会影响 CacheManager，必须先接通配置再调整数值。

建议的初始策略如下，属于调参起点，不是已生效配置：

| 缓存内容 | 建议起点 | 更新规则 |
| --- | --- | --- |
| 标准、产品、筛选列表 | 5 分钟新鲜期，最多允许旧结果保留 30 分钟 | 仅在允许返回旧数据的页面后台刷新，并返回数据更新时间；规则或数据版本切换后不混用 |
| 条件总数 | 10 分钟 | 仅复用与页数据相同版本的精确总数；不把估算值冒充精确分页总数 |
| 文件可用状态 | 正向 60 秒，负向 10 秒 | 文件变化时失效；扫描未完成、NAS 不可达时保留“未知”，不要缓存成“无文件” |
| 筛选字典、单位联想 | 根据实际更新频率设置，先低优先级处理 | 基础数据导入后刷新；联想按完整条件缓存 |

旧结果返回需要接口提供 `data_version`、`updated_at`、`refreshing` 等字段；只缓存总数或只缓存页数据时，另一部分必须取同一版本。无法取得同一版本时重新读取，不能拼接出相互矛盾的分页。

当前单机部署可先保留本地 SQLite：使用 WAL、短写事务、合理的 busy timeout 和定时清理。WAL 允许读写并行，但同一时刻仍只有一个写者，不能把它当成无限并发缓存。缓存库应放本机磁盘；跨主机部署或写入竞争经测量成为瓶颈后，再迁移 Redis。参考 [SQLite WAL](https://www.sqlite.org/wal.html)。

跨进程刷新租约至少包含缓存键、持有者标识和过期时间。计算过程在事务外执行，发布结果和释放租约时核对持有者及版本，避免租约过期后的旧任务覆盖新结果；等待者要有超时和重试上限。

### 3. 第二阶段：建设一条标准一行的查询汇总表

建议实体表命名为 `std_search_index`，每个 `base_id` 一行。它保存列表常用字段与预计算结果，详情和下载仍使用原始标准及文件记录。下面是逻辑字段草案，落地前需按真实 schema 确认类型、长度、字符集和空值规则。

| 字段 | 用途与约束 |
| --- | --- |
| `base_id` | 主键，保持原标准 ID；不按标准号重新选择另一条记录 |
| `std_id`、`std_id_norm`、`std_id_compact` | 展示、规范化等值及前缀查询；规则与现有解析器对齐，不给 compact 字段贸然加唯一约束 |
| `std_name`、`std_name_norm` | 原名称和预先规范化名称，减少查询时逐行 REPLACE |
| 标准类型、执行状态、发布日期 | 列表显示、筛选和排序；类型编号与原文本分别保留，避免改变原有模糊匹配 |
| `release_year`、`std_year` | 分别保存发布日期年份和标准号年份，保留当前年份筛选的两者 OR 逻辑 |
| `pdf_filter_match` | 按当前 SQL 的文件名匹配条件预计算，初次切换用于保持列表筛选结果一致 |
| `has_matching_pdf`、`matching_pdf_count` | 按现有 Python 标准号匹配规则计算的记录状态及数量；不代表磁盘实时可读 |
| `preferred_file_id` | 默认展示或下载候选；其他匹配文件仍可查询，不能只检查此文件就判定整条标准可用性 |
| `source_revision`、`indexed_at`、`rule_version` | 追踪源数据批次、构建时间和规则版本，服务于刷新、缓存失效和回退 |

当前 SQL 的紧凑字符串包含匹配与 Python 的 `filename_contains_std_id` 不是完全相同的规则。初期同时记录两个结果，输出差异清单；若以后统一为严格匹配，应单独评估结果变化，不能在性能改造中悄悄减少搜索结果。

文件路径、磁盘检查时间和可读状态建议保存在按文件记录或路径组织的索引中，再汇总到标准。状态区分“已确认存在、已确认缺失、不可读取、尚未检查”；附 `checked_at`。列表复用最近状态，点击下载时再次验证并处理实际读取失败。

多文件、单位、地区、产品仍保留关系结构。例如一条标准有 2 个 PDF 和 5 个单位，直接 JOIN 会产生 10 行；按标准汇总可避免这类乘法展开。地区与单位名组合筛选、单位位次、目录条件必须保留现有关系语义，不能用逗号拼接字段代替；目录筛选需要考虑全部相关文件，不能仅看默认文件路径。

候选索引与首页查询示例，均为设计草案，尚未执行：

```sql
CREATE INDEX idx_search_pdf_date
    ON std_search_index (pdf_filter_match, release_date DESC, base_id DESC);
CREATE INDEX idx_search_std_compact
    ON std_search_index (std_id_compact);

SELECT base_id, std_id, std_name, release_date, has_matching_pdf
FROM std_search_index
WHERE pdf_filter_match = 1
ORDER BY release_date DESC, base_id DESC
LIMIT 10;
```

预期改变是：查询不再遍历文件表、逐行规范化文件名来判断 PDF 匹配，而是按已计算的标记读取标准。该索引主要针对首页；类型、状态等组合是否另建索引，应根据高频查询及 EXPLAIN 决定。复合索引遵循左侧前缀规则，不能指望一个索引优化所有条件。参考 [MySQL 复合索引](https://dev.mysql.com/doc/refman/8.0/en/multiple-column-indexes.html)。

发布日期如果当前存为文本，应先检查格式、空值和异常值，再决定是否转换 DATE；转换不得改变既有有效记录的排序。加入 `base_id` 作为同日期记录的排序补充条件，可以稳定翻页；这是需要回归确认的排序改动。参考 [MySQL LIMIT 与排序](https://dev.mysql.com/doc/refman/8.0/en/limit-optimization.html)。

### 4. 汇总表如何刷新

1. 首次离线构建影子表，按批读取标准和文件记录，在后台完成规范化与匹配。构建数据库汇总时不对每条记录同步访问 SMB；磁盘状态由独立任务更新。
2. 固定构建数据的时间点。存在可靠变更日志时记录水位并补放构建期间的变更；没有可靠日志时明确它是某个快照的结果，展示快照时间，并安排下一次重建，不能宣称零延迟同步。
3. 比对总数、记录集合、筛选和排序后发布新版本；表与版本切换保持原子性，保留旧版本供回退，避免页面读到构建到一半的表。
4. 后续增量更新按受影响的 `base_id` 重算。标准修改、文件新增/删除/改名/迁移、单位和规则变化都要覆盖；文件从 A 标准改挂 B 标准时，A、B 都需刷新。
5. 若采用可变汇总表，批次更新与数据版本在同一事务提交；查询在一致性读中取得版本、总数和页数据，缓存只写入对应版本。不要先发布版本、再分批更新旧数据。
6. 外部程序也会写源库时，仅在本应用接口加刷新钩子不完整。先确认全部写入来源，再选择导入完成回调、可靠时间戳加删除记录、变更日志或定期全量比对；不能假设现有表一定有可用更新时间字段。
7. NAS 扫描单独运行，合并重叠根目录，由一个扫描任务供全部 worker 读取持久索引。失败或未完成的扫描不得把已有文件批量标为删除，最后一次完整扫描的时间需要可观察。

建议先采用“每次数据导入后刷新，加定期校对”的简单方式。只有确认变更来源和刷新时限后，再增加更复杂的持续同步；索引刷新与 ZIP 任务都应限流，避免后台优化反而拖慢交互请求。

### 5. 中文检索需要单独优化

汇总表能消除关联匹配和运行时字符串变换，但 `%化妆品%` 仍可能扫描大量名称。不能据此承诺所有搜索都变成毫秒级。

- 标准号使用已规范化字段进行等值、前缀匹配，保留年份、分册、T/Z 等现有区别；混合输入继续按当前规则解析。
- 中文名称优先在测试副本验证 MySQL InnoDB 的 ngram FULLTEXT，覆盖原名称与规范化名称的实际检索需求。MySQL 内置 ngram 支持中日韩文本，默认 token 长度为 2；相关设置和停用词会影响结果。参考 [MySQL ngram 文档](https://dev.mysql.com/doc/refman/8.0/en/fulltext-search-ngram.html)。
- 全文候选检索不等同于任意子串 LIKE。只有证明候选覆盖旧结果的输入类型才切换；再用原匹配规则过滤。短词、特殊标点、停用词、标准号混合输入保留兼容路径。只做最终过滤无法找回候选阶段漏掉的结果。
- 同类产品使用全部展开词的候选并集，再按现有主词权重计算排序。不能只取全文前 100 条再统计，从而把截断数量当成精确总数。
- 若功能要求复杂中文分词、纠错和多字段相关度，或 MySQL 测试未达到目标，再评估独立搜索服务。引入前需要说明同步延迟、运维成本和故障时的回退路径。

### 6. 前端、分页与下载之间的配合

列表第一次请求返回必要展示字段和带时间的文件状态；重复渲染不再无条件启动一轮十条标准的磁盘检查。需要更新状态时使用批量查询、短缓存和后台刷新，磁盘状态变化只更新相应行。用户能区分“最近检查可用”和“尚未检查”，下载继续实际验证。

关键词或筛选变化时取消旧请求，并用请求序号阻止迟到响应覆盖新结果。浏览器缓存加入 TTL、数据版本和进行中请求合并；页面切换复用结果，同时给过期内容安排一次刷新。

初期保留现有页码与精确总数，用独立总数缓存减少开销。只有产品允许时再改成首屏先显示、总数稍后补齐。深分页若实测成为瓶颈，可为连续翻页提供游标；游标应包含筛选、完整排序键和版本，关键词得分排序及空日期需要分别处理，版本变化时重新开始。任意跳页仍需单独设计，不能直接用游标替换全部分页。

下载侧同时推进本地 ZIP 后台任务、稳定 GET URL 和 Nginx 直传，详见[下载性能检查报告](/home/zkbz01/download_file/下载性能检查报告.md)。缓存和汇总表不会提高用户网络带宽；将打包及慢客户端传输移出同步 worker，可以减少它们对搜索请求的排队影响。

### 7. 实施顺序与验收

| 顺序 | 交付内容 | 验收重点 |
| --- | --- | --- |
| 第一步 | 分阶段计时、产品缓存、共享总数、请求合并和预取限流 | 重复搜索不再执行完整慢 SQL；同一条件多个并发请求只计算一次；翻页复用总数 |
| 第二步 | 汇总表构建、版本刷新、首页查询切换 | 查询计划不再为首页 PDF 判断全扫文件表；固定数据快照下结果集合一致 |
| 第三步 | 中文候选索引与高级筛选接入 | 冷搜索耗时下降；召回、排序、单位位次、年份和目录语义通过对比 |
| 同期下载改造 | 有界 ZIP 任务、预览复用、本地归档、Nginx 下载 | 大包生成和传输期间，搜索等待不被明显放大；Range、失败重试和清理行为正确 |

候选性能目标：本机接口结果缓存命中 P95 不超过 100 毫秒；汇总表首页取页加有效总数缓存 P95 不超过 300 毫秒；常见中文搜索冷请求 P95 争取 1 秒以内。这些是待验证目标，尚未达到，也不含用户网络或浏览器渲染。第一步先验证当前慢请求有明确下降，再用结构改造争取目标，不以单次最快值验收。

验收记录至少包括缓存命中/过期/等待次数、COUNT 与取页 SQL 时间、磁盘检查时间、响应总时间、队列长度、数据库连接数及 CPU/RSS。连接池按每进程配置，总连接预算需要乘 worker 数，再计入后台任务，不能只看单个池大小。

正确性在同一固定数据快照下比较原查询和新查询的总数、完整 ID 集合及顺序。173867、412、483 是本次基线，数据更新后不能继续把这些数字当成固定正确答案。加入标准号变体、空名称、同日期排序、多文件、目录、多单位、省市区、单位位次大于 3、产品词库更新、两个年份来源、文件删除和 NAS 暂不可达等样本；新增稳定排序时单独核对相同排序值的记录。

性能测试区分 SQL/结果缓存命中、未命中和文件缓存状态，并在测试环境覆盖 1/3/5 个并发用户、翻页、变更后刷新、缓存击穿及下载同时进行。冷缓存实验使用独立缓存命名空间和测试数据，不清空线上缓存或生产机器全局文件缓存。每阶段保留原查询回退开关，出现结果差异或刷新失败时可恢复旧路径。
